# The checking aid

`aid` is the Python package of the checking aid of the Bachelor End Project. It reads a supplier's order confirmation, or a captured webshop cart page, compares it by fixed rules with the purchase order as Exact holds it (the version of the order that the document answers, with the values the buyer entered in Exact and ticked since that version was filed), carries out the routine corrections, asks the supplier the standard questions, and hands the buyer only the cases its rules cannot settle. What it does and why is in the [design specification](../docs/superpowers/specs/2026-10-26-checking-aid-design.md); the build, task by task, is in the [implementation plan](../docs/superpowers/plans/2026-10-26-checking-aid-implementation.md).

How to use the aid day to day, run it on the company side, maintain it and solve problems: [MANUAL.md](MANUAL.md) (with a one-page Dutch guide for the buyer at its end).

## Install and test

Python 3.11 or newer (developed on 3.13; the suite also passes on 3.11). From the repository root:

```bash
python3 -m pip install -r aid/requirements.txt -r aid/requirements-dev.txt
python3 -m pytest aid/tests -q
```

The test suite runs offline: no test makes a network call or calls an AI service. A test that needs an AI answer replays a recorded one, made on made-up documents only.

## Try it out on the made-up set

Two commands run the whole aid on the made-up document set, with no AI service, no credential, no company document and no connection: the writer prepares changes in a CSV file and nothing is sent, so nothing reaches any system. A question is written as an .eml file only where the settings say `"send_via": "file"` (the folder of `--prepare-only`, below); without a way to send it is not asked at all and goes to the buyer as "Bericht niet verzonden".

```bash
python3 -m aid.demo --out demo
python3 -m aid.review --settings demo/settings.json
```

The first command writes `demo/settings.json` (the example settings with the parser as the reader and the folders under `demo/`) and `demo/cases.csv` (the 20 confirmations and the 2 saved cart pages with their PO numbers), files the made-up PO PDFs and, as looks at their two POs, the two ERP exports into `demo/po_store/`, runs every case and prints the statuses. With the parser the two scans fail, as expected: a scan has no text layer, so only the LLM reader can read it; `python3 -m aid.demo --out demo2 --reader recorded` replays the recorded LLM answers of the test fixtures instead, so every document is read, still without any call. Look at `demo/summary.csv` (one row per case), a case folder `demo/cases/<PO number>_<time>/` (`steps/01_po_versions.json` to `08_result.json`, `audit.json`, `write_log.jsonl`, `dispositions.csv`) and `demo/cases/prepared/prepared_changes.csv`, the changes prepared for Exact: the review page lists a price, a delivery date, a quantity and an article's purchase price on its tab "In Exact invoeren", for the buyer to enter, and the buyer attaches the confirmation and sets the status Bevestigd in Exact himself.

The second command serves the review page on http://127.0.0.1:7860 (the host only; `--share` is refused with company settings): the cases in review, each with its two documents, the three lists, the four decisions per item and the article tick, the close button and the undo, in Dutch with a switch to English. Its tab "Beoordelen" opens with a strip that counts the cases by their state and names what is wrong with the aid, with a button that opens the section of "Instellingen" that handles it, and a fold with every case of the last 7 days and what the buyer does about it; the page reads them, the case list and the count in the tab's name again every 30 seconds, from the aid's own files, without touching the case that is open. After the cases in review the case list offers the cases the aid could not finish ("mislukt: zelf bekijken") and the documents it could not place ("Document scan.pdf, 2026-11-12 17:03, zelf bekijken"), each with why in words and the document itself, to handle in Exact and to note with "Als afgehandeld noteren", which writes `handled_by_hand.json` into the case's folder, or a line to `cases/review_items_handled.jsonl` for a document, and nothing else. Closing a case writes its prepared changes and its dispositions; the undo reverses a written change. A question ("Leverancier vragen") needs the supplier's address under "Leveranciers" on the tab "Instellingen" and a way to send. This folder's settings name none, so the page asks nothing, keeps the case with you and says "Er is geen postvak verbonden: verbind een postvak onder Instellingen, Postvak en AI, en sluit de zaak opnieuw af."; on a folder made with `--prepare-only` (below), whose settings say `"send_via": "file"`, the question is written to `live/cases/outbox/*.eml`, sent to no one, and the case waits. Its tab "In Exact invoeren" lists the prepared changes that the buyer enters in Exact, one row per change with its order, its line and article and the old and the new value, to tick as entered or as not to enter (the ticks go to `demo/cases/prepared/marks.jsonl`); the digest's first line counts them and links to the tab (`?tab=invoeren`). Its tab "Prijslijst" compares a supplier's price list with the purchase prices of that supplier's articles, which the buyer gives as an export from Exact (kept per supplier in `cases/exact/article_prices.json`): "Bekijken" shows what changes and writes nothing, and one press puts the changes on the list of the tab "In Exact invoeren", where the article prices of one price list are ticked with one press. Of an Excel file the aid reads the one sheet the buyer sees, wherever it reads one, and a CSV row with a filled cell beyond its column titles refuses the file, and so does, in a file cut at commas, a row with another number of cells than its row of column titles. Four kinds of rows the tab shows and keeps off the list: a price of an article that another supplier holds too, by its export or by an open change on the list (the row names that supplier); a price more than three times as high or as low as the purchase price in Exact (a price per 100 read per piece); a price that the list holds as ticked already; and a price that the buyer took off the list. One press beside the supplier's field takes the purchase prices kept for a supplier away, for a supplier given under two spellings. Its tab "Bestanden" takes a file the buyer gives on the page (a PO PDF, a confirmation, an e-mail saved as .eml, and an export once its columns are set) into the watched folder for the runner's next pass, and lists the last lines of what the runner did, a line for each document, each attachment of an e-mail and each case checked again, as `cases/intake.jsonl` holds them. Its tab "Instellingen" holds five sections: the buyer's own settings as a form ("Uw regels": the thresholds, the wait, the digest, the addresses), the suppliers, the work mailbox and Copilot ("Postvak en AI"), the connection to Exact, and "Stand van de assistent", which shows the runner's last pass, the launcher, the mailbox, what reads the documents and the last lines of `runner.log`, read from the files of this PC. It shows what `demo/settings.json` holds each time the tab is selected, each save names what it saves and writes into that file only what was changed on the form, and the aid uses the new values from its next pass. The section "Koppeling met Exact" sets the layout of the purchase orders that Exact e-mails, from one sample PDF with a trial read, and the words and the digits by which the aid finds the order number on a confirmation, and in its part 2 the columns of the export of order lines, from one sample export with a trial read; `aid/madeup/tryout/ANDERS_po_v1.pdf` and `aid/madeup/tryout/EXPORT_nl.csv` are made-up samples to try them on, as the manual's section 3.17 shows step by step. At the end of that block, with `test_mode` switched on there and no authorization limit set, the part "Proefdraaien met een inkooporder uit Exact" makes a made-up confirmation of a purchase order the aid knows, with one difference to choose, reads it back, and offers it for download or puts it into `demo/inbox/` for the runner's next pass (`aid/tryout.py`); the aid sends nothing about a case made from it (`aid/tryout_mark.py`). A confirmation that names an order the aid does not know yet waits on the review tab with a hint that names the order, and the runner checks it again by itself as a new case once that order comes in (section 3.17). The page answers its own host only: open it as 127.0.0.1 or localhost.

The runner is the loop both hosts run, and the way the aid works by itself: a confirmation that arrives is the trigger. To watch it, prepare a second folder without running any case (a document a folder has seen once counts as a duplicate afterwards, so the `demo` folder above would skip the made-up confirmations), start the loop, and drop a confirmation into its inbox from another terminal:

```bash
python3 -m aid.demo --out live --prepare-only
python3 -m aid.runner --settings live/settings.json --poll-seconds 5
cp aid/madeup/out/MU03_conf.pdf aid/madeup/out/MU07_conf.pdf live/inbox/      # in a second terminal
```

Within one pass the two files move to `live/inbox/processed/`, two case folders appear under `live/cases/` (PO 250103 closed with its prepared changes, PO 250107 for review), the questions whose wait is over are escalated, and when the digest is due (`digest_time` in the settings) the digest is written to `live/cases/digests/` and, as an .eml, to `live/cases/outbox/`. To get a digest after every pass with a case, start a review page on this folder's own settings file, `python3 -m aid.review --settings live/settings.json` (stop the page of `demo/` first, or the new one takes the next port), and choose "Na elke zaak" under "Dagoverzicht" on its tab "Instellingen"; or set `"digest": "per_case"` in `live/settings.json`. The tab writes the settings file its page was started with, so the page of `demo/` would change `demo/settings.json`, which the loop on `live/` does not read. Create the file `live/STOP` to end the loop. On the company side the mailbox rule does the copying. The other commands take made-up inputs the same way: the price-list import (`python3 -m aid.pricelist --file <list.csv> --supplier S01 --current <current_prices.csv> --prepared demo/cases/prepared --settings demo/settings.json`), the necessity check (`python3 -m aid.evalscripts.necessity --cases aid/madeup/out --spec aid/madeup/spec --recorded aid/tests/fixtures/recorded --out demo/necessity.csv`) and the freeze record (`python3 -m aid.freeze --settings demo/settings.json --out demo/freeze.json`).

The pre-check in the browser works the same way on a prepared folder. The demo's settings hold a made-up capture token, so the capture server starts on them, and `--testshop` makes it serve the two made-up cart pages as a test shop:

```bash
python3 -m aid.capture_server --settings live/settings.json --testshop
```

Load the browser extension of `aid/extension/` unpacked in Edge or Chrome, put the token of `live/settings.json` (`capture_token`) in its options and open http://127.0.0.1:7870/testshop/CART02.html: within about a second an amber banner at the top of the page names the PO line that is not in the cart and the price difference, with a link to the case on the review page (stop the review page of `demo/` and start `python3 -m aid.review --settings live/settings.json`, so that the link finds the case), and CART01 gives a green banner. A reload answers from the same case. The extension sends the cart page to the server on this computer only; [extension/README.md](extension/README.md) describes the options and the check by hand.

One command starts the three together instead: `python -m aid.start --settings live/settings.json --testshop` starts the runner, the review page and the capture server, keeps them running (a part that ends is started again) and writes their output to `live/logs/`. That launcher lives in the terminal it was started in: closing the terminal stops the three parts. Add `--background` (`python -m aid.start --settings live/settings.json --testshop --background`) to start it apart from the terminal, which can then be closed. `python -m aid.start --settings live/settings.json --status` shows how they are, `--stop` creates `live/STOP` and waits for all three to end, and `--resume --background` deletes `STOP` and starts them again, in the background (`--resume` alone starts them in the terminal). The two addresses are fixed, so only one launcher runs on a PC: a start that finds a review page or a capture server already answering starts nothing and says so (a launcher on other settings is stopped with `--stop` on its own settings, a part started by hand is closed). On Windows, `python -m aid.start --settings live/settings.json --testshop --install-autostart` makes Windows start them at every logon, in the background and without a window, and starts them at once; `--remove-autostart` takes that away. When the word `python` does nothing in the terminal (on Windows it may be a placeholder for the Microsoft Store), call the launcher with the full path of the Python, for example `C:\Users\<you>\AppData\Local\Programs\Python\Python311\python.exe -m aid.start ...`: the launcher starts the parts and the start at logon with the same Python. [MANUAL.md](MANUAL.md), section 3.4, describes the launcher.

On a Windows PC where nothing can be installed, the aid runs from a folder that holds its own Python and its packages, and the buyer starts it with a double click. Build the folder once on a Windows PC with a 64-bit Intel or AMD processor, with the Python that is to run it and the aid's packages installed: `python -m aid.portable --build C:\Users\<you>\Inkoopassistent`. The build downloads python.org's embeddable Python of the same version. It checks the package's sha256 itself only for the versions in `EMBED_SHA256` (`aid/portable.py`: 3.13.12 to 3.13.17, 3.14.3 to 3.14.10, 3.15.0 to 3.15.2); for any other version, 3.11 among them, it prints the sha256 and the md5 for you to compare with the version's release page on python.org before the folder is used. It installs the packages of `aid/requirements.txt` into the folder with pip (without the development client's library), copies the program (the files git tracks under `aid/`, without the tests, and names any other file it leaves out) and writes three start files and a `LEESMIJ.txt`; on another system it builds nothing and says where to run it. Copy the folder to the PC where the aid runs, onto its local disk and not into a folder that OneDrive synchronises, and double-click `Inkoopassistent starten`: the first start writes `data\settings.json` (the example settings with the parser as the reader and a random capture token), sets the start at logon, starts the three parts in the background and opens the page; from then on they start at each logon. `Inkoopassistent stoppen` stops them until the next start, `Inkoopassistent niet meer vanzelf starten` takes the start at logon away. On the PC every document stays in the folder's `data`, and the aid puts only a few other things elsewhere (the shortcut for the start at logon, the Microsoft sign-in in the user's profile, and in the browser the history of the page). [MANUAL.md](MANUAL.md), section 3.16, describes the folder and lists them.

With your own Anthropic key, the demo can read the made-up documents live through the development client: put the key in the environment (`export ANTHROPIC_API_KEY=...` on macOS or Linux, `$env:ANTHROPIC_API_KEY="..."` in PowerShell; never in a file of the repository or the demo folder) and run `python3 -m aid.demo --out demo3 --reader anthropic`. Every confirmation and the cart screenshot then go to the service, the decider is asked where the rules call for it, and the audit of each case names the model; a run over the 22 cases costs a small amount. This option is for made-up documents only: a company document goes to Microsoft 365 Copilot through the work sign-in and to no other service, so the runner (the company-side command) has no such option.

What the demo does not do: write to Exact or send mail. The aid writes nothing in Exact at all: from the buyer's seat no program reaches it, so the buyer enters each change of a price, a delivery date, a quantity or an article's purchase price from the tab "In Exact invoeren", attaches the confirmation and sets the status Bevestigd in Exact himself (the digest marks those "(zelf in Exact doen)"), and `exact_base_url` must stay empty: no command builds a write route into Exact, and a settings file that sets the key is refused ([MANUAL.md](MANUAL.md), section 3.10). The SMTP mailer needs the aid's mailbox. Setting `authorization_limit` in `demo/settings.json` turns the re-approval rule on for the made-up POs above it. For the AI service on company documents, the runner uses Microsoft 365 Copilot through the user's own work sign-in ([The AI service](#the-ai-service)); it needs a Copilot licence on the account, seven permissions on the app registration and an administrator's consent for four of them, so the demo does not use it.

## Layout

One module per step of a case, in the order a case goes through them: `sources/` (mailbox.py: the watched folder; microsoft_mail.py: the work mailbox, read through Microsoft Graph into the watched folder; upload.py: a case from files; capture.py: a case from a saved cart page; dropin.py: a file given on the review page, put safely into the watched folder), `readers/` (po_pdf.py: the PO PDF; supplier_parser.py: the template parser; supplier_llm.py with llm_client.py: the LLM reader; copilot_client.py: Microsoft 365 Copilot, the AI service, behind the LLM reader's client interface; cart.py: a saved cart page; po_export.py: an export of PO lines, Excel or CSV; pdf_text.py: the text layer), po_store.py (the PO versions), versioning.py (which version the document answers), matching.py (document lines to PO lines), comparison.py (the scoring manual's rules), routing.py (the settings table, R01 to R11), execution/ (ops.py: the write operations; writer.py: the prepared writer, the retrying writer, the write log and the undo; exact_api.py: the Exact writer, which no command builds; by_hand.py: the list of the prepared changes the buyer enters in Exact, with his ticks, and the values those ticks say Exact holds, which the pipeline lays over the PO version it selected before it compares), messaging/ (the supplier questions, the re-approval request, the mailers, the reply wait; microsoft_mailer.py: sending through the work mailbox), audit.py (the audit record), pipeline.py (run_case, the dispositions, the escalation), batch.py (headless runs over a case list), notify.py (the digest), review/ (the review page), capture_server.py with extension/ (the pre-check of a webshop cart in the browser), runner.py (the loop both hosts run), start.py (one launcher for the runner, the review page and the capture server, and the start at logon on Windows), portable.py (the aid from a folder that needs no installation: its build on a Windows PC, its start by a double click and at logon), pricelist.py (the price-list import, and the article prices of the exports from Exact, kept per supplier, that the review page compares a price list with), tryout.py (the try-out confirmation made from a stored PO, for the owner's test in the test mode, read back before it leaves the page), tryout_mark.py (what tells a try-out document apart, and the guards that keep a case made from one from a supplier, the approver and the live system: it sends nothing, and it writes through the prepared writer only, never through the Exact writer), evalscripts/ (the reading scorer, the bake-off, the necessity check), freeze.py (the freeze record), madeup/ (the made-up document set) and colab/ (the notebook for the made-up set). Beside them stand connections/ (secrets.py: the protected store of the sign-in's tokens on the PC; microsoft.py: the Microsoft sign-in), decider.py (the open questions the rules leave, such as which PO version a document answers), schema.py (the document model and its normalisers), case.py (the case folder: what each module writes into it is listed in its docstring) and settings.py (the settings model). The tests live in tests/, with the recorded LLM answers under tests/fixtures/recorded.

The commands, from the repository root, with their required options:

```bash
python3 -m aid.batch --cases <cases.csv> --po-dir <folder> --settings <file> --reader parser|recorded [--recorded-dir <folder>] --out <summary.csv>
python3 -m aid.runner --settings <file> [--poll-seconds N] [--max-passes N]
python3 -m aid.review --settings <file> [--share]
python3 -m aid.capture_server --settings <file> [--host 127.0.0.1] [--port 7870] [--testshop]
python3 -m aid.start --settings <file> [--testshop] [--poll-seconds N] [--background] [--status | --stop | --resume | --install-autostart | --remove-autostart]
python -m aid.portable --build <folder> [--python-zip <file>]
python3 -m aid.pricelist --file <price list .csv or .xlsx> --supplier <supplier> --current <prices.csv> --prepared <folder>
python3 -m aid.evalscripts.necessity --cases <folder> --spec <folder> --recorded <folder> [--out <file>]
python3 -m aid.freeze --settings <file> [--out <file>]
python3 -m aid.evalscripts.bakeoff --models <model id> [<model id> ...] [--estimate-only]
```

`--reader recorded` of the batch needs `--recorded-dir`. Each command's `--help` lists its other options.

## Settings

Everything the buyer controls is a setting: the price thresholds, the supplier lists, the wait for a supplier's answer, the digest, the language and the folders. [settings.example.json](settings.example.json) lists every setting with its default, and `settings.py` holds the model with the allowed values. A key the model does not know is refused, so a misspelled setting stops the aid instead of being ignored.

Copy the example to a `settings.json` outside the repository and fill it in. These values live only there:

- the real e-mail addresses of the buyer, the aid's mailbox and the approver (the example holds `example.com` addresses), and the buyer's name that signs the aid's messages (`buyer_name`, empty in the example);
- the buyer's authorization limit, the PO total above which a changed PO goes back to the approver (the example holds `null`);
- the supplier lists, the lead times and the suppliers' e-mail addresses to which the aid sends its questions (`supplier_emails`), which name real suppliers;
- the capture token (`capture_token`, `null` in the example), which the browser extension sends to the capture server (`python3 -m aid.capture_server`) and without which the server does not start; the extension's options hold the same value.

`ms_tenant_id`, `ms_client_id`, `mailbox`, `mail_folder`, `mail_folder_name` and `send_via` connect the work mailbox through the user's own Microsoft sign-in (`aid/connections/`, `aid/sources/microsoft_mail.py`, `aid/messaging/microsoft_mailer.py`). In the example they are `null`, and `send_via` is `"auto"`: the aid then works as before, from the watched folder. They are filled in on the settings tab of the review page: the Directory (tenant) ID and the Application (client) ID of an app registration in Microsoft Entra ID (identifiers, no secrets), the address of the mailbox to read and send from (`null`: the signed-in account's own; another mailbox needs the shared permissions of the registration and access in Exchange), and the id and the display name of the folder that the runner reads at each pass (`null`: no mailbox is read). `send_via` says how messages go out: `"microsoft"` through that mailbox, `"smtp"`, `"file"`, or `"auto"`, which, with a folder set, is the mailbox whenever an account is signed in at the time of the message, else SMTP when it is set up, else nothing: the runner and the review page then send no question or request and write none as a file, and each goes to the buyer as "message not sent" (only the digest is written into `cases/outbox/`). While the sign-in has lapsed, `"auto"` and `"microsoft"` send no question (it goes to the buyer as "message not sent") and the digest is written into `cases/outbox/`. The sign-in's tokens are kept in a protected store on the PC, never in the settings file or a repository. While a tenant or a folder is set, the review page's `--share` is refused. The manual's section 3.14 gives the steps of the app registration and of the connection.

`reader` says how the documents are read: `"llm"`, by Microsoft 365 Copilot through the same Microsoft sign-in, which needs `ms_tenant_id` and `ms_client_id` (the runner refuses `"llm"` without them), or `"parser"`, by the template parser, without AI. The settings tab sets it ("Documenten lezen met"); the manual's section 3.15 gives what Copilot needs.

`exact_base_url`, `exact_endpoints` and `exact_fields` are the keys of a write route into Exact that no command builds: the address of a web API, the path of each endpoint, and the field name of each kind of change whose field differs from the writer's default. The writer behind them (`aid/execution/exact_api.py`) was written against a stand-in of the tests and never run against Exact, and it fits no door of Exact Globe+. `exact_base_url` must stay `null` or empty: a settings file in which it is set is refused at the start of the runner, the review page, the capture server and the launcher, and the aid prepares every change for the buyer to enter (MANUAL.md, section 3.10). `smtp_host`, `smtp_port` and `smtp_user` give the mail server and the login of the aid's mailbox (`null`: no mail server; messages are written as `.eml` files only with `"send_via": "file"`). The mailbox password is no setting: the runner reads it from the environment variable `AID_MAIL_PASSWORD`. There is no Exact token: no command reads `AID_EXACT_TOKEN`.

Relative paths in the file resolve against the folder that holds the settings file, not against the working directory. The credential of an AI service is not a setting: a client reads it from the environment or from the platform's secret store, never from the settings file or from code (see [The AI service](#the-ai-service)).

`po_layout` and `po_senders` let the aid read the PO PDFs that the ERP e-mails (`aid/readers/po_layout.py`, `aid/readers/po_pdf.py`, `aid/sources/mailbox.py`). `po_layout` describes the layout of that PDF in words that stand on its page: the text before the PO number and before the other header values, the words of the row of column titles and what each column holds. With it every PO PDF is read with this layout and with nothing else, and a PDF that fits it is filed as a PO. `po_senders` lists the senders of those e-mails, one address or one domain to each entry; when it is filled, a PDF in the PO layout that came in an e-mail from another sender is handled as a confirmation. Fill it whenever `po_layout` is set: without it a supplier's document that repeats the PO's page is filed as a PO. In the example they are `null` and `[]`: the aid then reads only the made-up PO layout. Both are company values, set on the company side and kept out of the repository: the settings tab of the review page sets them in its section "Koppeling met Exact" from one sample PDF of the company's own purchase order, after a trial read that shows what the layout reads and each problem the reader would meet, and writes them into the settings file only when the sample can be filed with them (the manual's section 3.17). While either is set the review page's `--share` is refused. The made-up PO `aid/madeup/tryout/ANDERS_po_v1.pdf` is in a second made-up layout for trying this out; the manual's section 3.12 gives its layout, the keys and the rules.

`test_mode` (`false` in the example) says that the aid works with the test account of Exact, for the owner's test before the hand-over: while it is `true`, whatever the authorization limit, the tab "In Exact invoeren" says to enter its changes in the test Exact only, and only the switch on the settings tab ends it, not a limit; while it is `true` and no authorization limit is set, the settings tab offers the try-out confirmation of `aid/tryout.py`, read back before it leaves the page, and the watched folder takes it (`aid/tryout_mark.py`); under the same condition the tab offers a try-out cart for the pre-check, read back likewise, which the capture server serves under `/tryout/` and takes from the extension. The first start of the folder version writes it `true`; the hand-over starts with an empty data folder and switches the test mode off on the settings tab, as a step of its own (the manual's sections 3.16 and 3.17).

`precheck_suppliers` is reserved and has no effect yet: no module reads it. The cart pre-check runs through the capture server for the browser extension, or through the batch (`python3 -m aid.batch`, a row of kind `cart` in its cases file). Both check a cart against its PO as the PO store holds it, where the ERP exports that give a cart its PO side are filed by the runner, from the watched folder or an e-mail, and by the batch, from its `--po-dir`. The batch is given the PO number of each cart. The capture server finds it (`aid/sources/capture.py`): the number the cart page states, else the one order filed on the day of the cart (its export was given that day) that holds exactly the cart's items and is not sent; any other choice by the items is a guess, for which the aid prepares nothing and the buyer checks the order on the review page. A cart that was checked before its order was filed (a grey banner), or whose order was a guess, is checked again when its page comes again: when another order is found, or the aid is now sure of the order, a new case is opened, and the earlier one is finished as replaced unless the buyer decided something in it. The earlier cases of the same cart lines that still wait untouched go with it, as the guess of the cart before the order's number was typed into it (the manual's sections 2.5 and 3.13). Under a match and under differences the banner's last line says what a cart check does not compare: delivery time, minimum or pack quantity, delivery costs and delivery terms.

`export_columns`, `export_decimal_comma` and `export_fill_down` describe the export of PO lines, an Excel (.xlsx) or CSV file saved from an overview of the ERP, which gives a cart pre-check its PO side because no PO PDF exists before ordering (`aid/readers/po_export.py`). `export_columns` maps the aid's field names of a PO line to the column titles of the file. Each key is one of `po_number`, `line_id`, `item_code`, `description`, `quantity`, `unit`, `unit_price`, `price_basis`, `discount_pct`, `net_price`, `delivery_date` and `supplier`, and its value is the title of the column that holds that field. The map must name `po_number` and `item_code`; a field it leaves out is missing on the PO, and without `line_id` the lines of each PO are numbered in the order of the file. Map `supplier` only to a column that holds the supplier exactly as the supplier lists of the settings name it, since they are keyed by that name. An empty map, the default, means that the export names each column after its field, as the made-up exports do (`aid/madeup/out/CART02_export.csv`). `export_decimal_comma` (default `false`) says how the file writes a number as text: `true` for 1.234,50, `false` for 1,234.50; a number cell of an Excel file is read as the number it holds either way. `export_fill_down` (default `false`) is set to `true` when the file prints the PO number once for each PO, on its first line or on a row of its own above its lines. The settings tab of the review page sets the three from one sample export of the company, after a trial read that shows the first and the last order as the aid reads them and each problem the reader would meet (the manual's section 3.17); while `export_columns` is set the review page's `--share` is refused. With these three settings the runner files an export it finds in the watched folder or on an e-mail, once `export_columns` is not empty, and the batch runner every `*_export.csv` of its `--po-dir`. Each PO of an export becomes a look at that PO, kept beside its PDF versions as `po_store/<PO>/e<n>/po.json`, and an export with the same rows files nothing; a cart is checked against the PO as it stands, the latest look when it came after the latest PO PDF, and a confirmation against the PO PDFs while there are any. The manual's section 6 says what an export may look like and what makes the aid refuse one, and `aid/madeup/tryout/EXPORT_nl.csv` is a made-up export in a Dutch form to try the settings on.

`article_columns` and `article_decimal_comma` describe the export of a supplier's articles with their purchase prices, an Excel (.xlsx) or CSV file saved from Exact, which the tab "Prijslijst" of the review page compares a supplier's price list with (`aid/pricelist.py`, `aid/review/pricelist_page.py`). `article_columns` maps `item_code` and `price`, and `supplier` only for an export that names the supplier of each row, to the column titles of the file; part 3 of the block "Koppeling met Exact" of the settings tab sets both from a sample, with a trial read, and while `article_columns` is empty the tab offers nothing. The column titles of each supplier's price list are no setting: the tab keeps them with its data, in `cases/exact/pricelist_columns.json`, when a list is put on the list "In Exact invoeren", so that no press of the tab changes the settings file. While `article_columns` is set the review page's `--share` is refused.

## The AI service

The AI service of the aid is a Microsoft service of the Copilot family in the company's tenant. The company supervisor stipulated that the AI platform must be Copilot and that the data are for internal use only (recorded feedback of 30 October 2026, in the thesis repository's `docs/meetings/`). The researcher decided on 2 November 2026 that any AI service of Microsoft's Copilot family is acceptable, and on 8 November 2026 the company's AI service was named as Microsoft 365 Copilot. The model sits behind one interface, `LlmClient`, so the service can change without changing the modules that use it.

- Company documents are processed only through Microsoft 365 Copilot (`CopilotClient`, `aid/readers/copilot_client.py`), used with the user's own work sign-in through the Copilot Chat API of Microsoft Graph. The client sends the text layer of a PDF with its lines numbered, and the reader checks every value against the page, so a value Copilot takes from elsewhere is marked uncertain; web grounding is switched off. A scan has no text layer and is not read, nor is a PDF with a scanned page (a blank page is left out): its case is listed as failed in the digest. The Chat API is a preview of Microsoft, in Graph's beta endpoint, which Microsoft does not support for production use. No credential of the AI service is a setting: the sign-in's token is kept in the protected store on the PC. The manual's section 3.15 gives what Copilot needs and how to connect it.
- Made-up documents contain no company data and may be processed anywhere, in Google Colab or locally. The Anthropic client (`AnthropicClient`) is the development client for made-up documents only: the SDK reads `ANTHROPIC_API_KEY` from the environment (in Google Colab, from Colab Secrets).

No company document, no content taken from one and no identifying metadata goes to any other AI service (the Anthropic client included) or to Google (Colab, Drive). Runs on company documents are hosted on the company side, in the company's Microsoft environment or on a company PC that the company designates. Google Colab with a Drive folder is kept for the made-up set only. The runner for the company side is described in [Running on the company side](#running-on-the-company-side); its host and folder follow the company's answer.

## Running on the company side

The runner (`aid/runner.py`) runs the aid as a loop: every 60 seconds it handles the watched folder, runs each new case, ends the wait of the questions that bounced or had no answer in time and makes the digest when it is due, until a file `STOP` exists next to the settings file. In the watched folder an e-mail that answers a question of the aid (its In-Reply-To or References header names the Message-ID of a question the aid sent, not of a re-approval request) is filed into that case under `messages/replies/`, `messages/bounces/`, `messages/auto/` or `messages/own/`, and opens no case: a reply puts the case in review with the item "supplier answered: read the reply" and reports it in the next digest, so that the buyer reads it and decides, and a bounce ends the wait of its question at once; an automatic message (an out-of-office notice, a mail server's notice of a delay) and an e-mail of the aid's own side (the buyer's own reply to all) change nothing. A reply belongs to the question it names, so a case with two questions out waits until each has a reply of its own, and a case that waits while no question of it is out comes back to the buyer at the next pass. An export of the order lines in the watched folder or on an e-mail, an .xlsx or .csv file with the column titles of `export_columns`, is filed first, as looks at its POs (MANUAL.md, section 3.13). Instead of the mailbox rule, the runner can read a folder of the work mailbox itself after a Microsoft sign-in on the settings tab of the review page, and saves each new e-mail into the watched folder at the start of a pass (MANUAL.md, section 3.14); it reads the settings file again when the tab saves it. A case whose run was cut off after a write or a message is not run again, since that would repeat them: it goes to review with the item "run cut off after writes: check the write log". Errors go to `runner.log` under `cases_root`, each once in a run of the loop, and the loop goes on; a settings file that does not validate stops the command with exit code 2 and the fields at fault, never their values. Its command is

```bash
python3 -m aid.runner --settings <root>/settings.json [--poll-seconds N] [--max-passes N]
```

for the folder layout `<root>/{settings.json, inbox/, cases/, po_store/, STOP}`; prepared changes go to `cases/prepared/`, and messages written instead of sent to `cases/outbox/`. With `"reader": "llm"` it reads through Microsoft 365 Copilot with the work sign-in, and it refuses `"llm"` with exit code 2 while the settings lack the tenant and the client; with `"reader": "parser"` it reads with the template parser. A refusal or an outage of Copilot while a case runs leaves the case without a result, logged once, for a later pass. Only a failure of Copilot as a whole makes the other cases of that pass wait too, and the digest then says so in one line with the number of cases waiting; a refusal of one document holds back no other case, and a document Copilot keeps failing is finished as failed after three failures. It prepares every change in `cases/prepared/`: the buyer enters a price, a delivery date, a quantity or an article's purchase price in Exact from the review page's tab "In Exact invoeren", whose count the digest's first line gives, and attaches the confirmation and sets the status Bevestigd in Exact himself (`exact_base_url` must stay empty: no command builds a write route into Exact, and a settings file that sets the key stops the runner with exit code 2: MANUAL.md, section 3.10); it sends through the aid's mailbox when `smtp_host` and `smtp_user` are set and `AID_MAIL_PASSWORD` is in the environment; with no way to send it asks nothing and writes no file, and each question or request goes to the buyer as "message not sent" with its cause in the case's record (MANUAL.md, section 3.7), while `"send_via": "file"` writes the messages as files. The settings file with the real values lives in `<root>` only.

The aid reaches the work mailbox through the Microsoft sign-in on the settings tab of the review page (MANUAL.md, section 3.14), and Exact through the buyer, who enters what the page's tab "In Exact invoeren" lists (MANUAL.md, section 2.6). The first run on documents of the test account needs the company's written permission. The review page is started on its own, on the host, with `python3 -m aid.review --settings <file> [--share]`, and is served on 127.0.0.1 of the host only, so it is opened in a browser on that machine. It answers only a request that names that host (127.0.0.1 or localhost, alone or with the page's port); any other Host header is refused, so that a web page elsewhere cannot reach the settings tab's saves through a domain name that points at the host. `--share` opens a public share link for the made-up set only: it is refused with company settings (exit code 2). Google Colab runs the made-up set only ([aid/colab](colab/README.md)).

## Teams via Power Automate

The aid e-mails its digest from its own mailbox (`aid_email`), or from the work mailbox when it sends through it (MANUAL.md, section 3.14), to the buyer (`buyer_email`): once a day from `digest_time` on, or per case when `digest` is `per_case` (`aid/notify.py`). The digest lists the cases the aid handled, with an undo link next to each write it made, and a link to the review page (`review_url`) for each case that waits for the buyer; while changes wait to be entered in Exact, its first line counts them and links to the page's tab "In Exact invoeren". A Power Automate flow outside the code relays the e-mail to the buyer in Teams, so that no AI service is connected to Teams. The flow has a trigger and an action:

- Trigger: a new e-mail whose subject starts with `[Inkoopassistent]`, from the sender the digest has (`aid_email`, or the work mailbox's address when the aid sends through it), in the mailbox that receives the digest ("When a new email arrives" of the Office 365 Outlook connector, with the sender and the subject filter set). The subject is "[Inkoopassistent] Dagoverzicht DD-MM-YYYY", or "[Inkoopassistent] Daily digest DD-MM-YYYY" in English. The prefix is the same in both languages, so the trigger works whatever the language setting.
- Action: post a message to the buyer in Teams with the e-mail's text ("Post message in a chat or channel" of the Microsoft Teams connector, posted by the Flow bot in a chat with the buyer), or an adaptive card built from the HTML version of the digest ("Post card in a chat or channel"). `send_digest` sends only the text, as the e-mail's body. The HTML version, with the same content as headings, lists and links (`Digest.html` of `aid/notify.py`), is not sent: the runner writes it to `cases/digests/<day>.html`, with or without a mailer, for a flow to pick up and build the card from. The runner sets up no flow.

If the flow is not allowed, the e-mail itself is the notification.
